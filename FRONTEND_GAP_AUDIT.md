# Toy Choir TV — Frontend Gap Audit

**Audit date:** 22 October 2026  
**Scope:** Existing React, TypeScript and Vite frontend; project requirements in [project-overview.md](./project-overview.md) and the current implementation record in [frontend/project-progress.md](./frontend/project-progress.md).  
**Additional client requirement files:** No other project-level client requirements document was found during this review.  
**Status:** Audit only. No application code or behavior was changed.

## Executive summary

The frontend already contains public landing, login and signup demonstrations; student learning pages; parent, teacher and administrator workspaces; fictional data; responsive navigation; and local-only controls. Routes render across all five user areas, the TypeScript/production build passes, and the reviewed browser routes produced no application runtime errors.

The clearest current functional defect is that lessons marked locked in the student lesson list remain navigable and can be marked viewed through their detail routes. There is also a visible mismatch between one practice record's stored status and the status shown on the Practice page.

Several larger journeys are intentionally illustrative rather than complete: learner linking and consent, real permission-denied states, audio submission lifecycle, booking checkout, and subscription cancellation. The project overview explicitly defers backend, authentication, payments, storage, and production access controls; these items are recorded as prototype or pre-production gaps, not as a request to add those services now.

## Priority definitions

- **Critical:** Blocks safe production use or creates an immediate severe user/data risk.
- **High:** Materially conflicts with a confirmed requirement or the documented accessibility target.
- **Medium:** An incomplete journey, edge case, or state that should be addressed before the corresponding flow is treated as complete.
- **Low:** A usability or polish improvement with a limited impact.

Priorities marked **production gate** are not claims that the frontend demo should implement backend behavior. They identify requirements that must be addressed before real learner data or accounts are introduced.

## Route and state coverage observations

- **Routes:** All registered public, student, parent, teacher and admin routes rendered in browser smoke checks. Unknown URLs render the public not-found page. An unknown lesson ID renders a lesson-unavailable state. No broken registered route was found.
- **Loading/error/empty:** The app has no remote data loading in this stage. Existing empty coverage is limited (generic table, lesson-plan resources, initial booking summary); there is no global error boundary or role permission-denied state.
- **Guardian privacy:** The public flow is parent/guardian-only and does not offer teacher/admin account creation. No passwords are stored. Learner profile/linking and guardian consent remain fictional placeholders.
- **Booking/subscription:** Session selection and a local summary work; no reservation, cart, checkout, payment, cancellation or backend state is performed. Subscription price/payment details are correctly marked unconfirmed.
- **Audio/review:** The student screen clearly says recording/upload is disabled. Teacher audio playback is a disabled placeholder. Revision request/new-attempt/teacher-review/teacher-approval are local state only; AI text is explicitly fictional.
- **Responsive check:** At 360 px, the landing page and sampled student, parent, teacher and admin pages had no document-level horizontal overflow. The student and role mobile navigation opened in browser checks. This is a smoke check, not a full tablet/device or WCAG audit.
- **Console/build:** `npm run build` completed successfully (TypeScript and Vite production build). `problems` reported no diagnostics. Browser navigation across 29 URLs produced no new `pageerror` or console error during the final smoke check. Older browser history contained Vite HMR websocket connection-refused messages after its development server had been stopped; those did not recur as application runtime errors after restarting the server.

## Recommended order for fixing

1. **Address C1 first:** Make lesson availability consistent across the list and detail route so a locked sample lesson cannot be opened or marked viewed.
2. **Fix C2 and define sample-state contracts:** Render each practice's own status and add tests so sample data and displayed state cannot drift.
3. **Improve accessibility (P1/P2):** Prioritise text contrast/size and closed mobile-menu keyboard behavior before expanding the child-facing interface.
4. **Complete mock journey previews (C3–C8):** Define the no-backend, no-payment demonstration states for practice/revision, booking/checkout/cancellation, subscription cancellation, and guardian consent/linking. Keep all real operations disabled.
5. **Clarify teacher progression edge cases (C4/C5):** Define what must be present before revision, review and approval actions are enabled; ensure approval state resets consistently when the demo workflow changes.
6. **Add state/error coverage (C9/P3/P5):** Add empty/error-boundary and later loading states as data becomes asynchronous; automate core route and interaction checks.
7. **Treat C10/C11 as release gates:** Before production data, plan and verify backend-enforced permissions, denied-access behavior, guardian verification/consent records, Australian data residency and vendor assurances. Do not attempt to meet these with frontend-only checks.
